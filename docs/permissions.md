# 역할 권한 정책

이 문서는 [이슈 #596](https://github.com/team-cowork/cowork-server/issues/596)에서 정한 제품 정책과 기존 데이터 전환 기준을 기록한다.
권한 합산 순서는 [Discord 공식 문서](https://docs.discord.com/developers/topics/permissions#permission-overwrites)를 따른다.

## 기본 역할과 합산

- 팀마다 삭제할 수 없는 `@everyone` 기본 역할을 하나 둔다. 현재 팀 멤버에게 자동 적용하며 사용자별 할당 행은 만들지 않는다.
- 기본 역할의 최초 허용 권한은 `message_read`, `voice_connect`, `project_read`다. 발언, 메시지 전송, 수정과 관리 권한은 관리자가 부여한다.
- 기본 역할 권한 변경은 기존 멤버와 신규 멤버에게 같은 방식으로 적용한다. 탈퇴하면 적용 대상에서 제외하고, 재가입하면 현재 기본 권한을 적용한다. 이전 사용자 정의 역할은 복구하지 않는다.
- 기본 역할과 모든 사용자 정의 역할의 허용 권한을 합산한다. 기본 권한의 `false`는 다른 역할의 `true`를 취소하지 않는다.
- 채널에서는 기본 역할의 덮어쓰기를 적용한 뒤, 사용자 정의 역할의 거부를 합산하고 허용을 합산한다. 같은 단계의 충돌에서는 허용이 우선한다.
- 역할 우선순위는 역할 관리 범위를 제한한다. 일반 권한 합산에는 사용하지 않는다.
- 역할과 채널 권한 정책의 변경에는 `manage_roles`가 필요하다. 일반 역할 관리자는 자신보다 낮은 역할만 관리하고, 자신에게 없는 권한을 부여할 수 없다. 프로젝트의 설정 수정 권한과 역할 관리 권한도 구분한다.
- 팀의 built-in OWNER/ADMIN은 리소스 정책을 우회한다. 팀에서 탈퇴한 사용자는 우회할 수 없다. 계정의 전역 ADMIN 여부로 팀 접근을 허용하지 않는다.
- 사용자별 채널 덮어쓰기는 추가하지 않는다. 역할별 덮어쓰기를 사용한다.

## 리소스 접근

텍스트 채널은 `message_read`, 음성 채널은 `voice_connect`가 있어야 노출한다. 비공개 채널은 역할의 기본 접근 권한만으로 열리지 않으며, 채널 정책의 명시적 허용이 필요하다. 다른 작업 권한이 있어도 접근 권한이 없으면 요청을 거부한다. 리소스 생성 사실 자체는 권한 우회 조건이 아니다.

프로젝트는 팀 역할의 `project_read`, `project_write`, `project_manage`, `project_reorder`를 상속하고 기존 프로젝트 역할 정책으로 덮어쓴다. 설정 수정은 `project_manage`, 콘텐츠 작성은 `project_write`, 순서 변경은 `project_reorder`로 구분하며 모두 읽기 권한이 필요하다. `manage_projects`는 팀 차원의 프로젝트 생성·삭제에, `manage_github`는 GitHub 연결 관리에 사용한다.

프로젝트 역할 생성·할당에는 프로젝트 읽기와 팀의 `manage_roles`가 필요하며, 자신에게 없는 프로젝트 권한을 부여할 수 없다. 거부 정책이 포함된 프로젝트 역할의 삭제·할당 해제는 숨겨진 상속 권한을 다시 허용할 수 있으므로 팀 OWNER/ADMIN만 수행한다.

비공개 프로젝트는 프로젝트 역할의 명시적 읽기 허용이 필요하다. 접근할 수 없는 채널과 프로젝트만 목록에서 제외한다. 접근 권한을 표현하기 위해 채널이나 프로젝트 멤버를 추가·삭제하지 않는다.

음성 입장 시 발급하는 LiveKit 토큰은 `voice_speak`에 따라 마이크를, `screen_share`에 따라 화면과 화면 오디오를 허용한다. 두 권한이 없으면 구독 전용 토큰을 발급한다. 방송 시작과 호스트 재입장은 `live_broadcast`를 추가로 검사한다. 시청자에게는 발행 권한을 주지 않는다.

## 기존 데이터와 배포

1. 각 서비스의 추가 마이그레이션과 새 이벤트 필드를 읽는 코드를 먼저 반영한다. 기존 역할은 `isDefault=false`이며 역할 ID와 할당은 유지한다.
2. Preference가 팀 멤버 이벤트 및 스냅샷 준비 과정에서 기존 팀과 신규 팀의 기본 역할을 생성한다. 기본 역할과 변경 이벤트는 같은 트랜잭션으로 기록한다.
3. 기존 프로젝트는 `isPrivate=true`로 전환해 기본 역할 도입으로 공개 범위가 넓어지는 것을 막는다. 새 프로젝트 생성 요청에서 공개 여부를 생략하면 공개 프로젝트를 만든다. 기존 프로젝트를 공개하려면 관리자가 명시적으로 변경한다.
4. 각 서비스의 스냅샷·체크포인트 준비가 끝난 뒤 권한 의존 API를 연다. 프로젝트 서비스는 팀 역할 스트림도 받아야 한다. 소비자 그룹 이름 변경만으로 데이터를 재구축하지 않는다.

접속 중인 음성 참가자도 5초 주기로 권한을 다시 확인한다. 접근이 회수되면 퇴장시키고, 발언·화면 공유 권한이 바뀌면 LiveKit 참가자 권한을 갱신한다. 방송 호스트의 방송 권한이 회수되면 방을 종료한다. 권한 projection이 준비되지 않았거나 방송 세션 조회가 실패하면 연결은 유지하면서 미디어 송수신을 일시 중단하고, 복구 후 현재 권한으로 갱신한다. Kafka 반영과 실제 재검증에 걸리는 시간만큼 권한 변경이 지연될 수 있다.
